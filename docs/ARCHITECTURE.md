# Архитектура Nexora

Документ для разработчика, который будет развивать проект. Коротко: интерфейс на Next.js App Router, данные в демо-режиме живут в клиентском хранилище, а серверный слой (PostgreSQL + Drizzle, сессии, права, изоляция компаний) уже готов и ждёт подключения экранов.

## Данные в демо-режиме

- `lib/demo/generate.ts` моделирует 760 дней работы агентства: лиды приходят из каналов с разной конверсией, часть становится клиентами и сделками, сделки проходят этапы и закрываются. Генератор детерминированный (seed 700), поэтому у всех одинаковая картина.
- `lib/store/crm-store.ts` (zustand + persist в localStorage) хранит снимок `CrmData` и даёт действия: `moveDeal`, `createLead`, `convertLead`, `toggleTask` и т. д. Набор действий повторяет будущие серверные действия один в один.
- При следующем визите даты сдвигаются на прошедшие календарные дни, чтобы «сегодня» в демо всегда было сегодня.
- Все цифры (KPI, воронка, графики, LTV, команда) считаются в `lib/metrics.ts` из сущностей, а не хранятся отдельно. Поэтому выручка на главной, в аналитике и в профиле клиента всегда сходится.

### Сфера компании

`config/industries.ts` описывает восемь наборов. Идентификаторы этапов (`new … won/lost`) общие для всех — меняются только подписи и вероятности (`workspace.pipeline` → `lib/stages.ts`). Поэтому метрики, автоматизации и база не зависят от сферы, а клиника видит «Запись → Приём → План лечения», а стройка — «Замер → Смета».

Генератор демо-данных берёт из набора названия услуг, сообщения лидов, задачи, заметки и диалоги. Основные цифры (выручка, конверсия) одинаковы во всех сферах: дополнительные данные идут из отдельного генератора случайных чисел.

## Серверный слой

Жизненный цикл любого изменения на сервере (`src/server/actions/deals.ts` — образец):

1. `requireTenant(permission?)` — читает сессию из httpOnly-cookie, находит участие пользователя в активной компании, проверяет право по матрице `can(role, permission)`.
2. Валидация входа той же схемой zod, что и форма на клиенте. Данные с клиента никогда не считаются доверенными.
3. Запрос всегда с условием `workspace_id = ctx.workspaceId`. Чужая и несуществующая запись выглядят одинаково — «не найдено».
4. Изменение, запись в историю этапов и в ленту — в одной транзакции.
5. Ответ формата `{ ok: true, data } | { ok: false, error, fields }` — форма показывает ошибки у полей.

### Как перевести экран с демо-режима на сервер

1. Добавить серверное действие по образцу `actions/deals.ts`.
2. В компоненте заменить вызов `useCrm((s) => s.moveDeal)` на вызов действия; для мгновенного отклика — `useOptimistic`.
3. Начальные данные страницы загружать в серверном компоненте через `getDb()` с фильтром по компании.

## Безопасность

| Задача | Решение |
|---|---|
| Аутентификация | Случайный токен 256 бит в httpOnly + Secure + SameSite=Lax cookie; в базе только SHA-256 токена (`sessions.token_hash`). Выход со всех устройств — удаление строк |
| Пароли | Поле `users.password_hash` под argon2id; вход через Google — `oauth_accounts` |
| Авторизация | Матрица ролей Владелец / Администратор / Менеджер / Сотрудник в `lib/permissions.ts`. Интерфейс по ней скрывает действия, сервер — запрещает |
| Изоляция компаний | `workspace_id` в каждой таблице с данными. Компания берётся из сессии, а не из запроса. Составные внешние ключи `(workspace_id, id)` не дают базе связать сделку с клиентом или сотрудником другой компании — даже при ошибке в коде |
| Целостность | CHECK-ограничения: сумма ≥ 0, у закрытой сделки есть дата закрытия, у выполненной задачи — дата выполнения, вероятность этапа 0–100 |
| Валидация | zod на клиенте и на сервере, ограничения длины полей |
| Секреты интеграций | Хранятся только зашифрованными (`integrations.secret_encrypted`, ключ `APP_ENCRYPTION_KEY`) |
| Журнал | `audit_log`: кто, что и когда изменил |

`npm run db:check` проверяет эти гарантии автоматически: поднимает Postgres в памяти, применяет миграции, заливает демо-данные и пробует сделать запрещённые записи.

Дополнительный уровень для продакшена — Row Level Security: приложение подключается отдельной ролью без прав владельца таблиц и в начале транзакции выполняет `select set_config('app.workspace_id', $1, true)`, а политика на каждой таблице:

```sql
alter table deals enable row level security;
create policy tenant_isolation on deals
  using (workspace_id = current_setting('app.workspace_id')::uuid);
```

## База данных

30 таблиц, миграции `drizzle/0000_init.sql` и `drizzle/0001_inbox_documents_plans.sql`:

- **Доступ:** `users`, `sessions`, `oauth_accounts`, `workspaces`, `memberships` (роль и должность в компании), `invitations`.
- **CRM:** `clients`, `leads`, `deals`, `deal_stage_history`, `pipeline_stages` (подписи и вероятности этапов компании), `tasks`, `notes`, `activities`, `notifications`.
- **Переписка:** `conversations` (канал, привязка к лиду, клиенту и сделке), `messages`, `reply_templates`.
- **Деньги:** `products`, `deal_items`, `documents` (позиции и реквизиты сохраняются снимком — выставленный счёт не меняется задним числом; номер уникален внутри компании), `sales_plans` (месяц — первое число, сотрудник только своей компании).
- **Настройка под себя:** `custom_fields` (значения в jsonb `custom` у клиентов и сделок), `saved_views`, `imports` (списки созданных id для отмены), `workspaces.requisites`.
- **Автоматизации:** `automations` (триггер, условия и действия в jsonb), `automation_runs` (журнал срабатываний).
- **Интеграции и оплата:** `integrations`, `subscriptions` (провайдер хранится строкой — Stripe, ЮKassa или CloudPayments подключаются без изменения схемы), `audit_log`.

Деньги — целые копейки (`bigint`), время — `timestamptz`. Для поиска дублей при вводе хранится `phone_digits` и индекс по `lower(email)`.

## Дизайн-система

- **Цвета** — токены в `app/globals.css`: светлая тема основная, тёмная подобрана отдельно, а не инвертирована. Нейтральная база и один акцент (`--primary`, фиолетовый). Цвета этапов воронки и источников проверены на различимость, в том числе для людей с нарушением цветовосприятия.
- **Шрифт** — Onest: кириллица и цифры одной ширины в таблицах (`.tabular`).
- **Глубина** — три уровня тени: `shadow-card`, `shadow-raised`, `shadow-overlay`.
- **Графики** — одна ось Y на график (количество сделок вынесено в отдельный график, а не на вторую ось), подсказка при наведении, легенда для двух и более серий, цвет следует за сущностью.
- **Состояния** — скелетоны при загрузке, пустые состояния с действием, понятные ошибки. Анимации короткие и учитывают `prefers-reduced-motion`.

## Автоматизации

`lib/automation-engine.ts` — чистые функции без побочных эффектов: на событие (`lead_created`, `deal_created`, `deal_stage_changed`, `deal_won`, по расписанию `deal_idle`, `task_overdue`) проверяются условия (сумма, источник, приоритет, этап, ответственный) и возвращается список действий. Хранилище применяет их и показывает уведомление. Конструктор считает, сколько раз правило сработало бы на ваших данных за 30 дней, — до включения.

## AI-ассистент

`lib/ai/mock-assistant.ts` распознаёт намерение вопроса (потерянные лиды, конверсия, сделки под риском, менеджеры, прогноз, план на день) и отвечает по данным CRM. Для подключения языковой модели достаточно заменить функцию `answer` на вызов API, передав ей только данные текущей компании.

## Оплата

Тарифы и лимиты — в `config/plans.ts`, интерфейс цен от них не зависит. Подписка компании — таблица `subscriptions` со статусами `trialing / active / past_due / canceled`. Вебхук провайдера обновляет статус и `current_period_end`; доступ к функциям проверяется по `workspaces.plan`.
